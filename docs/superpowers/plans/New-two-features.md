Two features: max-resolution default + H.264/H.265 encoding
All findings below are grounded in code already read. Conventions honored throughout: the pure-Dart boundary (lib/src/backend, non-plugin lib/src/capture, lib/src/config, capability_bootstrap.dart stay free of package:flutter; new plugin code goes in separate files), every command acked honestly, verification via dart run tool/verify_pure.dart (the only runnable gate in this shell; flutter test is yours to run).

Feature 1 — Default resolution = each camera's measured maximum
Today every camera's mode is seeded at the hardcoded 1280×720 (_seedModes, lib/src/agent/agent_coordinator.dart:53) even though the capability probe already measured each camera's real ceiling (CameraCapabilities.highestResolution).

Changes:

_seedModes: seed camera i at capabilities[i].highestResolution ?? config.resolution (probe failure keeps the 720p fallback).
main.dart:_startKiosk: after ensureInventory, derive the open geometry from camera 0's max (inventory.capabilities.first.highestResolution) and copyWith it onto captureConfig before cameraProvider.open(...); pass config: captureConfig to AgentCoordinator (currently omitted) so _modeFor/_setMode fallbacks match the real geometry.
AgentCoordinator.adoptInventory: also refresh _config from the new camera-0 max — it re-opens camera 0 via reconfigure → start → _openCamera(_config), so a stale _config would reopen at the old geometry while the modes claim the new max.
Tests in verify_pure.dart (+ mirrored flutter test): modes seeded per-camera max, fallback when probe empty, adoptInventory updates modes and _config, registration announcements carry the max label.
Docs: README capability section + docs/implementation-status.md.
Known caveat (documented, not fixed): cached capabilities are stored in declared form with the old 720p fallback folded in, so a sub-720p camera's declared max is 720p; presetForHeight clamps to the real ceiling exactly as today — no regression, strict improvement for every camera above 720p. Also: at 4K, takePicture may not hold 5 fps; the pump sheds (never queues) and the server would overstate duration_ms (media.md warns) — documented; switch_camera remains the escape hatch.

Feature 2 — H.264/H.265 via ffmpeg (LGPL _min build, hardware-first)
You chose LGPL hardware-first: dependency ffmpeg_kit_flutter_new_min (core ffmpeg, LGPL, app stays MIT). Software x264/x265 are GPL-only and excluded. Encoder availability is probed at runtime, never assumed (repo doctrine).

Wire contract (from server docs/protocol/media.md)
One recording.frame body = one access unit; bytes stored verbatim, length-prefixed, no container → emit raw Annex B elementary-stream AUs with in-band SPS/PPS (VPS for HEVC). EncodedFrame.isKeyFrame already models exactly this.

New pure-Dart modules (testable in verify_pure.dart)
lib/src/capture/annexb.dart — Annex B AU splitter: NAL walk (3/4-byte start codes), VCL NAL starts a new AU, non-VCL (SPS/PPS/VPS/SEI) attach to the following AU; keyframe = AU containing IDR (h264 type 5 / HEVC ≥19). Single-slice-per-frame assumption documented (true for our encoder args: -bf 0, one slice). Handcrafted byte-vector tests for both families.
lib/src/capture/batch_encoder.dart — BatchTranscoder contract (JPEG paths + args in → elementary-stream bytes out) and BatchVideoEncoder implements VideoEncoder: wraps the existing TakePictureFramePump, buffers captured JPEGs, flushes a batch when fps frames accumulate or 2 s elapse (single-flight; backlog beyond 2× batch drops oldest, counted and logged), writes JPEGs to a transient temp dir, awaits one transcode, splits AUs, emits EncodedFrames paired 1:1 with the source frames' seq/ts (count mismatch ⇒ whole batch dropped, never garbage), stop() flushes then cleans temp dir. Each batch is its own ffmpeg session ⇒ every batch starts with IDR + param sets ⇒ mid-stream-decodable at batch boundaries and natural GOP = batch size. This writes temp files in the frame path — a documented deviation ("no-disk path" stays deferred; files are per-batch transient, the price of ffmpeg_kit's imperative API).
New plugin-side files (outside the pure boundary)
lib/src/capture/ffmpeg_transcoder.dart — FfmpegTranscoder implements BatchTranscoder via FFmpegKit.executeWithArguments: -y -framerate F -i dir/f%05d.jpg -c:v <enc> -bf 0 -pix_fmt yuv420p -f h264|hevc out.bin. Encoder candidates per platform (Platform.isX, pattern as in camera_plugin_backend.dart:158): h264 → h264_mediacodec (Android), h264_videotoolbox (iOS/macOS), h264_mf (Windows, probed); h265 → hevc_mediacodec, hevc_videotoolbox; Linux likely none ⇒ mjpeg fallback, probe decides. Bitrate for hardware encoders derived from width×height×fps, one constant factor.
FfmpegCodecProbe implements CodecProbe — encodes one tiny embedded JPEG through each candidate at startup; session rc==0 and non-empty output ⇒ codec available. Never throws. Windows/Linux devices that lack encoders simply announce mjpeg and stay online.
Coordinator seam swap
Replace FramePumpFactory with EncoderFactory = VideoEncoder Function(CaptureCodec) (MjpegEncoder already wraps the pump byte-for-byte; BatchVideoEncoder for h264/h265). _onCapturedFrame consumes EncodedFrame; _producibleCodecs derives from the factory's measured supportedCodecs ∩ announced instead of isIntraOnly (the inter-frame objection no longer applies — the batch encoder carries state across frames within a batch). stop→dispose lifecycle per stream. Unbuildable codec ⇒ ok:false, never fake success. main.dart composes CompositeCodecProbe([BaselineCodecProbe(), FfmpegCodecProbe()]) and passes the factory; the main.dart:39 "added here and nowhere else" comment is honored.
