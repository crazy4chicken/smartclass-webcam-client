## 一、已确认的业务要求

这几条是需求，不是技术判断，改动需要用户同意。

1. **默认目标 1920×1080 @ 60fps。** 更高分辨率**仍写进能力声明**（运营侧可用  
   `switch_camera` 点上去），但**不作为默认**。
2. **先降帧率，保分辨率。** 1080p60 → 1080p30 → 1080p15，不降分辨率。  
   不支持当前请求时 `ack ok:false`，**绝不偷偷换成另一个 codec 或另一个模式再报成功**。
3. **codec 优先级：当前模式下可持续的 H.265 优先，否则 H.264，最后是 mjpeg。**
4. **每条带 `id` 的命令都必须 ack。**
5. **视频采集与编码在 native 内完成**，原始帧不跨入 Dart，视频路径不落临时文件。

## 二、已定的技术口径

这几条是实现决定，已落地并有门禁断言覆盖。

| 项         | 口径                                                    | 落点                                     |
| --------- | ----------------------------------------------------- | -------------------------------------- |
| 尺寸选择      | 取**实测**分辨率中 ≤1080p 且**与摄像头自身形状相同**的最大者；无实测用配置的几何      | `defaultResolutionFor`                 |
| 形状判断      | 交叉相乘比宽高比，不用浮点；**禁止只按像素总数猜几何**                         | `sameAspectRatio`                      |
| 帧率档位      | 取阶梯（5/10/15/20/24/25/30/50/60）中 **≤ 实测上限且 ≤ 60** 的最高档 | `defaultFpsFor`                        |
| 取整        | **只向下取整**，永不向上（实测 58 → 声明 50，不是 60）                   | `sustainableRates`                     |
| codec 可用性 | **按模式判定**：某 codec 在 30fps 可用不表示它在 60fps 可用            | `canServeMode` / `sustainableCodecsAt` |
| 证据缓存      | 键 = 格式版本 + 摄像头指纹 + 编码器身份；任一变化即失效；损坏当未命中               | `EncodeEvidence`                       |
| AU 边界     | 一幅图的多个 slice 合并为**一个** access unit；依据 slice 头的首片标志    | `AnnexBSplitter`                       |
| 落盘        | 视频路径无临时文件（native 内闭环）。**照片是否要求完全无磁盘未定**，见第四节          | —                                      |

**关于"声明 60 但交付 5–10"：** 这是**当前未修复的状态**，不是验收豁免。  
服务端用 `fps` 估段时长，所以该缺口会让段时长被高估；具体倍数**未查证，不重复引用**。  
在原生编码器落地前，`defaultFpsFor` 的 `unmeasuredFps` 参数仍由调用方传入  
`StreamSettings.fps`（= 60），即**无实测证据时仍声明 60** —— 这是已知缺口，  
不是"可以接受"。

## 三、门禁与验证口径

- 唯一主入口：`dart run tool/verify_pure.dart`。**断言数以实跑输出为准**，文档里不再写静态计数。
- 专项检查（`verify_annexb.dart` / `verify_encode_budget.dart` / `verify_default_mode.dart`）  
  **都由主入口调用**，且都做过变异验证（故意改坏实现，确认断言变红）。

## 四、三个开放问题的答复（2026-10-10 用户确认）

### 4.1 无实测证据时声明多少 fps？——声明下限，并把测量补上

**先澄清：摄像头检测测不出设备支持的帧率。** 现在的探针

（`plugin_capability_probe.dart` 的 `_acceptsFramerate`）做的是**接受性**测试：

用 `fps: 60` 打开相机，`initialize()` 不抛就算过。它证明的是"插件没拒绝这个数字"，

**不是**"真能以这个速率产出"。而五个平台的插件栈都**没有**报告真实帧率范围的 API

（`CameraDescription` 没有 fps 字段，`fps` 只是输入参数）。真正的上限由**采集路径**决定：

每帧一次 `takePicture()`，1080p 约 5–10 fps。所以"接受 60 / 交付 5–10"两者都对，

只是回答了不同的问题 —— 这正是缺口。

**决定：把"声明的帧率"和"请求的帧率"拆成两个数。**

| 概念                                   | 值                      | 用途              |
| ------------------------------------ | ---------------------- | --------------- |
| **请求帧率** `AppConfig.defaultFps` = 60 | 管线被要求跑到的上限（泵的 tick 间隔） | 允许高于交付量         |
| **声明帧率** `CameraMode.fps`            | 写进注册、被服务端用于估段时长        | **不得高于已证实的交付量** |

- **有实测证据时**：`defaultFpsFor` 取实测可持续的最高档（≤60），只向下取整。
- **无实测证据时**：声明 `kFpsWithoutEvidence = 5`（阶梯最低档）。**不再声明 60。**

  声明 60 而交付 5–10，会让服务端对每段时长的估计都错一个数量级，而设备侧完全看不出来；

  声明下限错得更少，且方向安全。
- **两者不再耦合**：泵仍按请求帧率 60 取帧，**不因为声明值低就节流** ——

  用户要的是高帧率，把交付量压到占位值上是本末倒置。

**测量怎么补** —— `lib/src/capture/sustained_rate.dart`：

- `SustainedRateMeter`：从**真实交付的帧流**里数出持续帧率。三条规则各堵一个高估：

  **预热期不计**（开头几帧最慢）、**只数新帧**（`videorate` 会靠重复上一帧凑数，

  数 tick 就会得到"60fps 但内容只有 15 帧"）、**窗口固定**（不是"跑到不想跑为止"）。

  只向下取整。`close()` 让"管线卡住/什么都没产出"也能收口 —— 零是**测量结果**，

  不是"没测"。
- `EncodeBudgetProbe`：平台实现接缝。跑真实管线一个有界窗口，产出 `EncodeEvidence`

  （版本 + 摄像头指纹 + 编码器身份）。**必须不抛**，测不了就返回 `empty`；

  **必须不报没看见过的速率** —— 拿探针的"接受率"去填测量行，正是这条接口要防的替换。
- 结果经既有的 `EncodeEvidence` 缓存与 `canServeMode` 校验，`defaultFpsFor` 自动从

  占位值切到实测值 —— **缺口会自己闭合，不需要再改决策**。

**当前状态**：模型、缓存、校验、接线**全部完成并有门禁断言**（含变异验证）；

**缺的是每个平台的 `EncodeBudgetProbe` 实现**。在那之前，设备声明 5。

#### 4.1.1 窗口标定与「最快样本」审查（2026-10-10：判据已写，策略待定）

**（a）预热与窗口长度：判据与算法已落地**（`lib/src/capture/rate_calibration.dart`）。

`SustainedRateMeter` 默认的 1.5s 预热 / 3s 窗口原本**没有实测依据**（"看着够长"）。现在有了判据：

> **一个窗口够长，当且仅当答案不再取决于窗口放在哪里。** 把窗口沿轨迹滑动，读数之间的  
> 最大相对偏差 ≤ `kSettledSpread`（10%）即视为收敛。

- `calibrateRateWindow()`：从预热阶梯 `0/0.25/0.5/1/2s` 与窗口阶梯 `0.5/1/2/4/8s` 里取  
  **最小**的收敛组合 —— 是"最便宜的够用测量"，不是"最漂亮的读数"。
- `rateSpread()`：单独暴露，让平台探针能直接&#x95EE;**「出厂默认值对这台硬件够不够」**。
- **收敛不了也是结果**：`settled: false` + 原因（"读数取决于窗口位置"），**不是**"没数据"。  
  一条持续降频的轨迹本来就不该被压成一个数。

**（b）「多窗口取最快样本是否代表持续能力」——结论：`max` 不是持续能力的证据。**

`EncodeSample` 记着"两次同几何的测量经常不一致（热状态），所以取最快的一次"。这句话对  
**"这台设备被看见到过什么"**&#x6210;立，&#x5BF9;**"这台设备可以被信任交付什么"不成立**：热降频下第一次最快，  
而长录像要的是**最后一次还能稳住**的速率。

`readRateSeries()` 因此把两个读数**分开报**，并把差距变成一个布尔：

| 读数                        | 含义                                           |
| ------------------------- | -------------------------------------------- |
| `peakFps`                 | 最快一次 —— **今天 `sustainableRates` 用的就是它（max）** |
| `plateauFps`              | 尾部中位数 —— 它**现在**还稳得住多少                       |
| `peakOverstatesSustained` | `peak > plateau × (1 + 容差)`，即"声明会高于实际"       |

> **待用户决策：注册里该写 peak 还是 plateau？** 工具已就位，改的是一行聚合策略。
>
> - **peak（现状）**：设备被公平对待；代价是热降频设备会**声明一个它已经不再交付的速率**，  
>   而服务端拿它估每段时长，**设备侧完全看不出来**。
> - **plateau**：与本节「声明不得高于已证实的交付量」「声明下限错得更少、方向安全」同向；  
>   代价是"冷机快、长期慢"的设备被低估一档。
>
> **定之前 `sustainableRates` 保持现状** —— 换聚合策略是行为变更，不自行扩大要求。

### 4.2 「无磁盘」的目的是什么？——为了速度、帧率与画质，不只是隐私

用户确认：**"无磁盘"的目的是"利用内存的速度，实现高帧率、高画质，以及不本地存储"。**

所以这是一条**性能要求**，不只是合规要求：

- 视频路径已经在 native 内闭环（原始帧不进 Dart、不落盘）。
- **照片路径目前不满足**：`TakePictureFrameSource` 走 `takePicture()` → 返回临时**文件**

  → `readAndDelete`，每帧落一次盘再删。要真正无磁盘，照片必须改走

  `ImageStreamFrameSource`（原始帧在内存里；`frame_source.dart` 里目前是

  `UnimplementedError` 占位）。
- 这也解释了为什么 native 编码是**唯一**的路：不是"换个 codec"，而是"换掉帧源"。

### 4.3 段时长用于计费吗？——不用于计费

用户确认**不用于计费**。因此 4.1 缺口的影响面是**检索/展示的时长准确性**，不是账单。

这降低了紧急度，但**不构成"可以继续声明 60"的理由** —— 声明值仍然是错的，

而且现在已经有正确做法了。段时长误差的**方向与倍数未查证**（旧记录的"高估 6–10 倍"

没有核对过服务端公式），**不要引用**。

## 五、平台顺序与暂停范围

- **落地顺序：Android → Windows → macOS → Linux。** 依据是"用户能编能跑"：  
  Android 有真机、Windows 就是这台机器；**Linux 本机谁都编不了**（缺 GStreamer/GTK/  
  `flutter_linux` 头文件）。原"Linux 优先"已作废。
- **Linux 原生编码继续暂停**，保留既有代码但**不宣称交付**。


  > **2026-10-10 修订（用户要求）：Linux 已从 release 流水线移除。** 原文写的是"Linux 构建仍在  
  > 四端 CI 内"，现已改为**不构建、不发布** Linux 产物。理由与本条一致、只是更严格：  
  > **不宣称交付的平台，就不该发出可下载的产物** —— 一个能装上的 Linux 包会被当成"这个平台支持"，  
  > 而它要交付的 1080p60 编码流在 Linux 上根本没实现。源码保留，`flutter build linux` 仍是将来  
  > 验它的第一步（见 `docs/linux-encoded-stream-status.md` 第六节）。
- 每个平台**独立验收**，任一平台达标都不替其他平台背书。
